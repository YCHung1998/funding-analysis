# Skeptic / Red-team Memo: position-funding-pnl ↔ paper-execution-engine Contract

Scope: read `position-funding-pnl/design.md` + `tasks.md` and `paper-execution-engine/design.md` + `tasks.md` at `develop@b370fa8`, plus the merged `risk-engine-kill-switch` design/spec. Default posture: find what breaks or needs rework. Findings split into CONFIRMED (verified by reading the actual text) vs PLAUSIBLE (reasoned, not textually certain).

## 1. Hidden coupling / maintainability risk

- **CONFIRMED — paper-execution-engine's real-module dependency is one-directional to `position-accounting` only, not `pnl-engine`.** `paper-execution-engine/design.md` Decision 6 states explicitly: "TradeResult、realized PnL 由 `pnl-engine` 訂閱終態事件產生；**本 change 不寫 TradeResult**." Task 3.1 only names `position-accounting` ("接上 `position-accounting` 的 hedge ratio / `classifyHedge`"). So the module-boundary split (position-accounting vs pnl-engine) does *not* force a direct import from both sub-modules — `pnl-engine` is consumed later, via an event subscription, not a function import.
- **CONFIRMED — the fake's interface shape is only partially pinned.** `paper-execution-engine` Decision 1 defines a `PositionReader { getOpenQuantity(leg_id): number }` port attributed to `position-accounting`. But `position-funding-pnl/design.md` **never mentions `PositionReader` or `getOpenQuantity` anywhere** — it only exposes `computeHedgeRatio`/`classifyHedge` (Decision 4) and internal Position fields (Decision 2). The `hedgeRatio`/`classifyHedge` fake surface is well-pinned (both docs agree on signature and return shape in their respective Decision 4/5). The `PositionReader.getOpenQuantity` fake is **invented unilaterally by paper-execution-engine** with no corresponding commitment on the position-funding-pnl side — real risk of divergence when the two converge (e.g., does `getOpenQuantity` return contract quantity or `base_quantity`? pfp design never says).
- **PLAUSIBLE** — because tasks.md 3.1 only says "未合併前以 fake 實作同一介面" without naming which party's doc is authoritative, if `position-funding-pnl` lands first without ever having specified `PositionReader`, the integrator will have to retroactively design that port's shape, risking rework in paper-execution-engine's fakes/tests built against a guessed shape.

## 2. Contract drift — `HEDGE_RATIO_CHANGED` ownership

- **CONFIRMED — no double-emission, ownership is consistent across both docs.** `position-funding-pnl` Decision 8's event table explicitly assigns `HEDGE_RATIO_CHANGED` to "`paper-execution` 雙腿協調者（使用本 change 的 `computeHedgeRatio`）", and Decision 4 repeats "`positionManager` 不發." `paper-execution-engine` Decision 4 confirms the same emission point ("在此之前只發 `HEDGE_RATIO_CHANGED`" — referring to `entryCoordinator`) and Decision 5 confirms it records both ratio bases. Both documents agree: single emission point = paper-execution's `entryCoordinator.ts`. No ownership ambiguity found.

## 3. Open Question 3 (`close_reason='KILL_SWITCH'`) — needs re-check NOW, not later

- **CONFIRMED — the gating condition position-funding-pnl was waiting on has already landed.** Git log shows `risk-engine-kill-switch` group 4 is merged (`05ae6c3 feat(risk): implement Kill Switch (C-16)`, archived at `openspec/changes/archive/2026-10-02-risk-engine-kill-switch/`). Its design.md line 189 states: "`close_reason`：因 Kill Switch 而結束的 Trade 用 `'KILL_SWITCH'`（規格書 §6 已有此值），即使經由 §15 緊急流程，以便統計區分" — i.e., the literal value `'KILL_SWITCH'` is confirmed stable regardless of tier (L1/L2/L3).
- **CONFIRMED — `position-funding-pnl` Decision 7 still only says "暫依淨值分類...Open Question" and tasks.md has no task that re-verifies this against the now-final 3-tier model.** Since the three tiers (`L1_STOP_ENTRY`/`L2_CANCEL_ENTRY`/`L3_FLATTEN`, only-escalate state machine) are final, this check can and should be done *before* task 4.1 implements `final_status`/`result_reason` classification, not deferred — "later" has already arrived. Recommend adding an explicit task-4.1 sub-step to cross-check L1/L2 (likely map to `ABORTED`) vs L3 (likely `EMERGENCY_EXIT`) against the existing `final_status` priority order, rather than leaving it as a dangling Open Question resolved only by narrative memory.

## 4. Ordering risk — tasks 3.2 and 4.3

- **CONFIRMED — task 3.2 depends on `funding-settlement-rules` (part of the already-merged `paper-trading-event-loop`), not on `paper-execution-engine`.** No execution-engine dependency found in Decision 6/8 text for funding amounts.
- **CONFIRMED — tasks.md line 2 mandates fixture Fills for all tasks** ("Fill 以固定 fixture 產生，不打任何交易所 API"), which is sufficient for 4.1–4.3's Position→FundingSettlement→TradeResult chain as far as *Fill* inputs go.
- **PLAUSIBLE, not textually pinned — task 4.2/4.3's trigger for `TradeResult` creation is under-specified on the position-funding-pnl side.** `paper-execution-engine` Decision 6 says pnl-engine "訂閱終態事件" (subscribes to Trade/Leg terminal-state events) produced by its own `entryCoordinator`/`exitCoordinator` via `makeTransitionEvent`. But `position-funding-pnl/design.md` Decision 7/8 never describes this subscription mechanism or the terminal-event schema it consumes — it only lists what `tradeResultAssembler` *emits* (`TRADE_COMPLETED`), not what triggers it to run. For task 4.3's scenario tests, the Trade/Leg terminal-state transitions will have to be hand-built as fixtures (consistent with the "no real API calls" rule), but since the event *shape* isn't specified by position-funding-pnl itself, those fixtures risk being built to a guessed schema that diverges from paper-execution-engine's actual `makeTransitionEvent` output — a second (milder) contract-drift risk beyond the `PositionReader` gap in §1.

## Bottom line

The dependency is genuinely one-directional for the modules that matter (hedge ratio/classifyHedge, Fill-driven accounting) — position-funding-pnl's tasks 3.2/4.3 do not require a real paper-execution-engine to exist, consistent with "不打任何交易所 API." The real risk is not ordering but **two under-specified fake surfaces**: `PositionReader.getOpenQuantity` (invented only in paper-execution-engine's design, never pinned by position-funding-pnl) and the Trade/Leg terminal-state event schema that triggers `tradeResultAssembler` (described only from paper-execution-engine's side). Recommend position-funding-pnl's design.md gain an explicit addendum defining both before either change's tasks 3.x/4.x land, to avoid rework at integration time. Open Question 3 (`KILL_SWITCH` close_reason) is unblocked now that Kill Switch group 4 has merged and should be resolved as part of task 4.1, not left open.
